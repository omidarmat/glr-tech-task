# نحوه اجرای پروژه

این پروژه با استفاده از کتابخانه React اجرا شده. با توجه به اینکه در متن تسک به لیست‌های بلند از مشتریان یا محصولات اشاره شده، از امکانات بهینه‌سازی ری‌اکت همچون هوک‌های useMemo و useCallback و همچنین memoکردن کامپوننت‌ها استفاده شده است. در فرایند اجرای پروژه کدنویسی تمامی قسمت‌ها به صورت دستی انجام شد و فقط در کامپوننت‌های جزئی مربوط به UI برای افزایش سرعت، از هوش مصنوعی استفاده شد. هوش مصنوعی در هیچ‌یک از تصمیمات مربوط به معماری و ساختار پروژه دخیل نبوده است.

# کتابخانه‌های استفاده‌شده در پروژه

لیست کتابخانه‌های استفاده شده در این پروژه به این شرح است:

```json
"dependencies": {
    "@ant-design/icons": "^6.3.4",
    "@tailwindcss/vite": "^4.3.3",
    "@tanstack/react-query": "^5.103.1",
    "@uidotdev/usehooks": "^2.4.1",
    "react": "^19.2.8",
    "react-dom": "^19.2.8",
    "react-hot-toast": "^2.6.1",
    "react-router": "^8.4.0",
    "tailwindcss": "^4.3.3"
  }
```

در ادامه توضیحاتی مختصر در مورد دلایل انتخاب هر یک از کتابخانه‌های فوق آمده است.

## Tanstack Query

این کتابخانه به این دلیل انتخاب شده که فرایند کش‌کردن دیتای دریافت‌شده از API را با استفاده از Query key ساده‌تر می‌کند. به همین ترتیب، Invalidate کردن دیتای کش‌شده در نتیجه‌ی Mutationها هم به واسطه‌ی استفاده از این کتابخانه بسیار راحت‌تر اجرا می‌شود و در مجموع استفاده از این قابلیت این کتابخانه به پرفورمنس اپلیکیشن کمک بسیاری می‌کند چراکه استراتژی کش‌کردن با Query key در این کتابخانه عملا مثل یک کانتکست ری‌اکت عمل می‌کند که به واسطه‌ی آن می‌توان کامپوننت‌های متعددی را از طریق آن تغذیه کرد، بدون اینکه گلوگاه‌های ری‌رندرشدن‌های بیهوده در نتیجه‌ی استفاده از کانتکست دردسرساز شود.

## React Router

اجرای فعلی پروژه شامل یک صفحه است، اما به منظور ایجاد امکان توسعه‌ی فرایند سفارش به صفحات متعدد، از این کتابخانه برای Routing استفاده شد.

## Tailwind

با توجه به محدودیت زمان در اجرای پروژه، کتابخانه Tailwind جهت افزایش سرعت استایل‌دادن به المنت‌ها استفاده شد.

## React Hot Toast

این کتابخانه برای نمایش نوتیفیکشن‌های استایل Toast استفاده شده. نوتیفیکیشن برای حالت‌های ناموجود بودن محصول یا افزایش و کاهش تعداد محصولات سفارش که در محدوده‌ی موجودی محصول نباشد در نظر گرفته شده اما با توجه به شکل پیاده‌سازی فعلی نوتیفیکیشن تریگر نمی‌شود.

# معماری پروژه

## ساختار فایل‌های پروژه

سورس کد پروژه در فولدی به نام src قرار گرفته که شامل موارد زیر است:

```
/components
/config
/constants
/contexts
/fake-data
/pages
/services
/types
App.tsx
AppLayout.tsx
Providers.tsx
```

کامپوننت‌های پروژه به تفکیک features و ui در پروژه ذخیره شده‌اند. البته با توجه به محدودیت زمان در اجرای فعلی، هیچ کامپوننت reusable در فولدر ui ذخیره نشده. اما ساختار در نظر گرفته شده برای این پروژه به این صورت است که کامپوننت‌هایی مانند دکمه‌ها، اینپوت‌ها، و سایر موارد تکرارشونده‌ای که به گرافیک رابط کاربری مربوط می‌شود در این فولدر قرار می‌گیرد. باقی کامپوننت‌ها که مختص فیچرهای به‌خصوص در پروژه هستند در فولدر features قرار می‌گیرند.

فولدر config برای ذخیره‌سازی تمامی اطلاعات و مقادیر ثابت مورد استفاده در اپلیکیشن استفاده می‌شود.

فولدر constants برای ذخیره‌سازی لیبل‌ها و سایر نام‌گذاری‌های ثابت در نظر گرفته شده است.

فولدر contexts برای ذخیره‌سازی فایل‌های مربوط به تمام کانتکست‌های مورد استفاده در اپلیکیشن در نظر گرفته شده است. ضمنا در این پروژه به دلیل اینکه اطلاعات و عملکرد اپلیکیشن در مورد stateها چندان نبود، از کتابخانه‌هایی همچون Redux یا Zustand استفاده نشد.

فولدر pages برای ذخیره‌سازی فایل‌های مربوط به صفحات اپلیکیشن در نظر گرفته شده. کامپوننت‌هایی که در ارتباط با Routeهای اپلیکیشن استفاده می‌شوند در این فولدر ذخیره می‌گردند.

فولدر services برای ذخیره‌سازی تمام هوک‌های دریافت دیتا از API در نظر گرفته شده است.

فولدر types برای ذخیره‌سازی تمامی تایپ‌های مربوط به موجودیت‌های اپلیکیشن در نظر گرفته شده است؛ هم تایپ‌های مربوط به داده‌های رد و بدل شده میان کلاینت و سرور هم تایپ‌های مربوط به کامپوننت‌های رابط کاربری

## ساختار انتقال داده‌ها

برای فرایند سفارش از کانتکست ری‌اکت استفاده شده تا دیتای مربوط به مشتری و محصولات سفارش در تمام قسمت‌های فرایند در دسترس باشد. البته برای انتخاب مشتری و لیست محصولات سفارش ۲ کانتکست مجزا در نظر گرفته شده تا از رندرهای غیرضروری پس از تغییر مشتری یا محصولات جلوگیری شود.

# کاستی‌های اجرای فعلی پروژه

## مشکل در لیست محصولات به دلیل استفاده از کتابخانه Faker

در پیاده‌سازی فعلی پروژه به دلیل استفاده از کتابخانه Faker برای تولید دیتای تست، هنگامی که از صفحه سبد خرید به لیست محصولات برمی‌گردیم، یا از صفحه لیست محصولات به لیست مشتریان برمی‌گردیم، محصولاتی که در حال حاضر در سبد خرید هستند، یا مشتری‌ای که پیش‌تر انتخاب شده بوده است، در لیست محصولات یا کاربان یافت نمی‌شوند چون لیست محصولات و مشتریان دوباره توسط کتابخانه Faker ساخته می‌شود و هیچ‌یک از محصولات و مشتریان که از نو ساخته‌شده‌اند با لیست مشتری‌ای که قبلا انتخاب شده یا محصولات قبلی که به سبد خرید راه یافته بودند یکی نیستند.

## مشکل حفظ‌نشدن سفارش بعد از ریفرش‌کردن

در حال حاضر، در صورتی که کاربر در میانه‌ی فرایند سفارش مرورگر خود را ریفرش کند، اطلاعات سفارش از بین می‌رود. برای حفظ سفارش در این سناریو برنامه‌ریزی‌شده بود که اطلاعات سفارش در Localstorage
ذخیره شود و در صورت ریفرش‌شدن مرورگر اطلاعات آخرین سفارش از آنجا بازیابی شوند اما به دلیل کمبود وقت فرصت اجرای آن فراهم نشد.

## بخش تایید نهایی کاربر و ثبت سفارش

به دلیل محدودیت زمان، فیچر تایید نهایی کاربر پیش از ثبت سفارش و همچنین ثبت نهایی سفارش اجرا نشده است.

## امکان ثبت سفارش بدون انتخاب محصول

در اجرای فعلی پروژه، در محدوده‌ی بیزینس لاجیک، از ثبت سفارش بدون انتخاب محصول جلوگیری به عمل نیامده. اما پیاده‌سازی UI به شکلی انجام شده که از ورود به صفحه فاکتور نهایی و ثبت سفارش بدون انتخاب محصول جلوگیری می‌کند.

## طراحی UI/UX اجرای فعلی

در اجرای فعلی پروژه، با توجه به محدودیت زمان، تمرکزی روی پیاده‌سازی UI/UX مناسب نداشتم و فقط به اجرای مکانیزم‌ها و عملکرد اپلیکیشن پرداختم. اجرای فعلی در واقع فاقد هرگونه کیفیت UI/UX است که در زمان مناسب باید طراحی شود.

## سناریوی خطا در دریافت اطلاعات از API

به دلیل محدودیت زمان اجرای تسک، سناریوی خطا در دریافت اطلاعات از API در اجرای فعلی پروژه پوشش داده نشده.
